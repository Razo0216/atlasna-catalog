1. Executive Summary

What we're building

Atlasna is a single-store online marketplace for Algeria — a digital-first mini-mart. One entity owns the inventory, sets pricing, and handles delivery. There is no multi-vendor support in this version — a deliberate scope cut, not an oversight.

  • Browse/search the catalog, view product detail pages
  • Auth — customer registration/login (JWT-based)
  • Cart → checkout → order, with CIB, Edahabia, and cash-on-delivery
  • Order tracking — placed → paid → packed → out for delivery → delivered
  • Admin product management (create/edit/delete/stock)
  • AI chatbot answering order status, pricing, and policy questions from real store data
Target platform: Google Cloud Platform. Two repos: atlasna_front (React/TypeScript) and atlasna-catalog (Java/Spring Boot).

Explicit non-goals (for now)

Multi-vendor marketplaceSeller payoutsInternational shippingNative mobile apps

API Gateway vs. Load Balancer — not the same thing, and we use both. Cloud Load Balancing distributes raw traffic and terminates TLS; it knows nothing about our business logic. 4. Cross-Cutting System Design Patterns

What, why, and when each one is introduced

4.1 API Gateway

What: one front door for all client requests. Why: without it, every microservice independently validates JWTs, handles CORS, enforces rate limits — duplicated logic and bugs. Tech: Spring Cloud Gateway.

Introduced: Phase 5

4.2 Load Balancing

Distributes traffic across multiple running instances so no single instance is overwhelmed, and traffic keeps flowing if one dies. Tech: GCP Cloud Load Balancing (L7).

Introduced: Phase 7 — meaningless before multiple instances exist

4.3 Rate Limiting

Two layers: gateway-level (coarse, per-IP caps) and Redis-backed token-bucket (fine-grained — login attempts, chatbot queries, checkout attempts). Protects against brute force, scraping, and cost blowout on LLM calls.

Introduced: basic version Phase 1, full version Phase 5

4.4 Resilience4j

Circuit Breaker — stop hammering a repeatedly-failing dependency, fail fast. Retry — transient blips retried with backoff. Timeout — no call waits forever. Bulkhead — caps concurrent calls to one dependency so it can't exhaust all threads.

Applied to: payment gateway, Vertex AI, Kafka producer, all inter-service calls.

Introduced: Phase 5

4.5 Kafka (event-driven architecture)

Placing an order triggers side effects (email, inventory check, low-stock alert) that shouldn't block the order itself or tightly couple services together.

TopicProducerConsumer(s)
order.placedOrder ServiceNotification Service, inventory logic
order.paidPayment ServiceOrder Service, Notification Service
inventory.lowCatalog ServiceNotification Service, Cloud Function
Introduced: Phase 5

4.6 Redis

1. Cache-aside for hot product reads. 2. Token-bucket rate-limit counters. 3. Chatbot short-term conversation memory, keyed by session.

Introduced: caching Phase 3, rate limiting Phase 5, chatbot Phase 11

4.7 MongoDB — deliberately narrow use

Not a Postgres replacement. Orders/products/users stay in PostgreSQL for relational integrity. Mongo is only for chatbot_conversations and audit_logs — flexible schema, no joins needed.

Introduced: audit logs Phase 3, chatbot logs Phase 11

4.8 GCP IAM

Least privilege — every service has its own service account with only the permissions it needs. Workload Identity lets a GKE pod assume a service account without a downloaded key file on disk.

Introduced: Phase 7, re-audited Phase 12

4.9 Cloud Functions (serverless, event-triggered)

GCP's Lambda equivalent. Planned: order confirmation email, low-stock admin alert, nightly sales report, product image thumbnail generation.

Introduced: Phase 7

9. Non-Functional Targets

  • API p95 latency: <300ms catalog reads, <800ms checkout
  • Availability target: 99.5% — realistic for this stage
  • All passwords BCrypt-hashed; all secrets in Secret Manager, never in git
  • Every inter-service call wrapped in Resilience4j once split into microservices
