01The big picture

What the app does, and how its layers fit together.

Atlasna is a single-store marketplace. There is one seller, the store itself, and two kinds of users:

  • ADMIN manages the catalog: creates, updates and deletes products.
  • CUSTOMER registers, logs in and browses. Ordering comes in a later phase.

Anyone can browse products without logging in. Only admins can change them. Logged-in users prove who they are with a JWT (a signed token) sent on every request.

The layers. A request goes down through them; the response comes back up.

Controller

Receives HTTP, validates the JSON body, calls a service, returns JSON. No business logic.

Service

The business rules: "emails are unique", "deleting a product hides it". Owns transactions.

Repository

Database access. Spring Data writes the SQL from method names like findByEmail.

DTO

The shape of JSON in and out. Keeps database entities, like the password hash, out of API responses.

03Life of a request

What happens between "Send" in Postman and the JSON coming back.

Every request takes this path. Any step can stop it early with an error.

flowchart TD
  A["HTTP request arrives on :8080"] --> B{"Authorization: Bearer … header?"}
  B -- no --> D
  B -- yes --> C["JwtAuthFilter: check signature + expiry,
load user from DB"]
  C -- valid --> C2["Request is now 'logged in as' that user"]
  C -- "invalid / expired" --> D["Request continues as anonymous"]
  C2 --> E
  D --> E{"URL rule allows it?"}
  E -- "no, and anonymous" --> X1["401 Unauthorized"]
  E -- yes --> G["Controller: validate JSON body"]
  G -- invalid --> X2["400 Bad Request + fieldErrors"]
  G -- ok --> H{"@PreAuthorize hasRole('ADMIN')
(write endpoints only)"}
  H -- "not admin" --> X3["403 Forbidden"]
  H -- ok --> I["Service → Repository → PostgreSQL"]
  I -- "not found / conflict" --> X4["404 / 409"]
  I -- ok --> J["200 / 201 / 204 + JSON"]

This app is stateless: the server keeps no login session. Each request carries its own proof of identity (the token), and the server forgets it once the response is sent. That's why SessionCreationPolicy.STATELESS is set.

04Authentication: who are you?

Registering, logging in, and how later requests prove identity.

How passwords are stored

Passwords are never stored. We store a BCrypt hash, like $2a$10$OUjvRSX2Rk…. BCrypt is deliberately slow and adds a random salt, so a stolen database can't be reversed into passwords quickly, and two users with the same password get different hashes. When someone logs in, BCrypt hashes the password they typed and compares the two hashes.

Register

POST /api/auth/register

sequenceDiagram
  participant Client
  participant AC as AuthController
  participant AS as AuthService
  participant DB as PostgreSQL
  Client->>AC: {fullName, email, password}
  AC->>AC: @Valid (email format, password ≥ 8 chars)
  AC->>AS: register(request)
  AS->>AS: email = normalizeEmail("Jane@Example.com") → "jane@example.com"
  AS->>DB: existsByEmail?
  alt already exists
    AS-->>Client: 409 Email Already In Use
  else new
    AS->>AS: hash password with BCrypt, role = CUSTOMER
    AS->>DB: saveAndFlush(user)
    Note over AS,DB: If two requests race, the UNIQUE(email)
constraint rejects one → 409, not 500
    AS->>AS: generate JWT
    AS-->>Client: 201 {accessToken, tokenType, expiresInSeconds, user}
  end

Everyone who registers gets the CUSTOMER role. There is no way to register as an admin; admins come only from the bootstrap.

Login

POST /api/auth/login. Spring Security's own components do the password check.

sequenceDiagram
  participant Client
  participant AS as AuthService
  participant RL as LoginRateLimiter
  participant AM as AuthenticationManager
  participant DAP as DaoAuthenticationProvider
  participant UDS as UserDetailsServiceImpl
  Client->>AS: {email, password} + client IP
  AS->>RL: checkAndRecordAttempt(email, ip)
  alt locked
    RL-->>Client: 429 + Retry-After
  end
  AS->>AM: authenticate(email, password)
  AM->>DAP: delegate
  DAP->>UDS: loadUserByUsername(email)
  UDS-->>DAP: User (with BCrypt hash)
  DAP->>DAP: BCrypt.matches(typed password, hash)
  alt wrong password or unknown email
    DAP-->>AS: BadCredentialsException
    AS->>RL: recordFailure(email)
    AS-->>Client: 401 "Invalid email or password"
  else correct
    AS->>RL: recordSuccess(email) (resets the count)
    AS-->>Client: 200 {accessToken, …}
  end
Why the message is always "Invalid email or password"

A wrong password and an unknown email get exactly the same response. If they differed, an attacker could use the login form to find out which emails have accounts. Spring's DaoAuthenticationProvider does this on purpose, and our handler keeps the message generic.

Every request after login

JwtAuthFilter, on every request that carries a token.

sequenceDiagram
  participant Client
  participant F as JwtAuthFilter
  participant JS as JwtService
  participant UDS as UserDetailsServiceImpl
  participant SC as SecurityContext
  Client->>F: GET/POST … Authorization: Bearer eyJ…
  F->>JS: extractUsername(token)
  Note right of JS: parsing verifies the signature.
Tampered or garbage → exception
  JS-->>F: "admin@atlasna.dz"
  F->>UDS: loadUserByUsername (fresh from DB)
  F->>JS: isTokenValid (same user, not expired)
  F->>SC: set authentication (user + ROLE_ADMIN)
  Note over F: Any failure (bad, expired, deleted user):
continue as anonymous, never crash
  F->>F: continue to the rest of the chain

The filter loads the user from the database on every request. The roles claim inside the token is informational only. If you delete a user or change their role, that takes effect on their very next request, even though their old token hasn't expired yet.

05Inside the JWT

What the token contains, and what stops anyone from forging one.

A JWT is three Base64 parts joined by dots: header.payload.signature.

eyJhbGciOiJIUzM4NCJ9.eyJzdWIiOiJ0ZXN0QGV4YW1wbGUuY29tIiwicm9sZXMiOlsiUk9MRV9DVVNUT01FUiJdLCJpYXQiOjE3OTAyMjc2MzcsImV4cCI6MTc5MDIzMTIzN30.usZU29HFah2ZLCMDkHFwVadc_VHgVh8d3Yk5P8OdHNPsdYDWFzHjYjLiJbW6j9_X
// header: which algorithm signed it
{ "alg": "HS384" }
// payload: the claims (anyone can read these; Base64 is not encryption)
{
  "sub":   "test@example.com",       // subject = the user's email
  "roles": ["ROLE_CUSTOMER"],
  "iat":   1790227637,               // issued at (Unix seconds)
  "exp":   1790231237                // expires 3600 s later
}
// signature = HMAC-SHA384(header + "." + payload, ATLASNA_JWT_SECRET)
  • Why it can't be forged: changing any character in the payload breaks the signature, and producing a valid one requires the secret, which only the server knows. That's why the secret must be long, random and never committed. The app refuses to start without one.
  • Payload is readable: never put anything secret in a JWT. We only put the email and role.
  • Algorithm: jjwt picks HS256, HS384 or HS512 based on the key's length. Our dev secret is 62 bytes, so it uses HS384.
  • No logout yet: a token stays valid until exp (60 minutes). Refresh tokens and revocation come with the frontend phase.

06Authorization: are you allowed?

Two layers of rules, and the difference between 401 and 403.

Layer 1: URL rules in SecurityConfig

These are checked top to bottom, and the first match wins. That's why the catch-all anyRequest() comes last.

RuleMatchesResult
"/api/auth/**"register, loginAnyone
HttpMethod.GET, "/api/products/**"list and view productsAnyone
"/actuator/health"health checkAnyone
anyRequest()everything else (POST/PUT/DELETE products…)Must be logged in
The Spring Boot 4 trap

The second rule passes HttpMethod.GET, an object. Writing "GET" as a string would be read as a URL pattern called "GET", which makes the rule protect nothing. It compiles and fails silently. We checked the Spring Security 7.1.1 jar to confirm the right signature.

Layer 2: method rules with @PreAuthorize

@PostMapping
@PreAuthorize("hasRole('ADMIN')")   // checks the user has authority "ROLE_ADMIN"
public ResponseEntity<ProductResponse> create(...)

Layer 1 answers "are you logged in?". Layer 2 answers "do you have the right role?". @EnableMethodSecurity on SecurityConfig switches layer 2 on. hasRole('ADMIN') looks for ROLE_ADMIN, which is why User.getAuthorities() adds the ROLE_ prefix.

401 or 403?

SituationStatusMeaningWhere it comes from
No token / bad token / expired token on a protected URL401"We don't know who you are"Authentication entry point in SecurityConfig → GlobalExceptionHandler
Valid customer token on an admin endpoint403"We know who you are; you're not allowed"@PreAuthorize → AccessDeniedException → handler
Bad token on a public endpoint200Public stays publicThe filter ignores the token and continues as anonymous

07Error handling

One JSON shape for every error, and one class that decides the status.

{
  "timestamp": "2026-09-24T05:28:25.682Z",
  "status": 400,
  "error": "Validation Failed",
  "message": "One or more fields are invalid",
  "fieldErrors": { "email": "Email must be valid", "password": "Password must be at least 8 characters" }
}
ExceptionStatusWhen
MethodArgumentNotValidException400Body fails @Valid rules; lists each field
HttpMessageNotReadableException400Broken JSON, or a bad enum value in the body
MethodArgumentTypeMismatchException400?category=NOPE, /products/abc
InvalidCredentials / BadCredentials401Wrong email or password
AuthenticationException401Protected URL without a valid token
AccessDeniedException403Logged in, wrong role
ResourceNotFoundException404Product missing or deleted

The 500 handler never reveals internal details to the client (no stack traces or SQL errors), because those help attackers. It logs them, so you can still debug.

08The product catalog

Five endpoints, paging, and why "delete" doesn't actually delete.

MethodPathWhoSuccess
GET/api/productsAnyone200 page of products
GET/api/products/{id}Anyone200 one product
POST/api/productsADMIN201 created
PUT/api/products/{id}ADMIN200 replaced
DELETE/api/products/{id}ADMIN204 hidden

Listing: which query runs

if (search is not blank)   → findByActiveTrueAndNameContainingIgnoreCase(search)
else if (category != null) → findByActiveTrueAndCategory(category)
else                       → findByActiveTrue()

So search wins if you send both. Spring reads ?page=0&size=10&sort=price,desc into a Pageable automatically. The response uses Spring Data's stable page format:

{ "content": [ …products… ],
  "page": { "size": 10, "number": 0, "totalElements": 3, "totalPages": 1 } }

Soft delete

DELETE sets active = false instead of removing the row. Public reads only return active products, so a deleted product shows as 404. The row stays so that future orders can still point to what was bought. Admin PUT can still find an inactive product by id.

Updates need no explicit save(). Inside a @Transactional method, Hibernate notices changes to a loaded entity and writes them when the transaction commits. This is called dirty checking.

09Rate limiting, CORS and CSRF

Protection against password guessing, and the browser-facing rules.

Login rate limiting

Per email: 5 failures / 15 min

Stops guessing one account's password. While locked, even the correct password gets 429, so guessing gains nothing. A successful login resets the count.

Per IP: 20 attempts / 1 min

Stops one client trying many accounts. Counts every attempt, successful or not.

Fixed window for one email, with a limit of 5

flowchart LR
  A["fail 1"] --> B["fail 2"] --> C["fail 3"] --> D["fail 4"] --> E["fail 5"] --> F["6th try: 429
Retry-After: 900"]
  F -.->|15 min after the first failure| G["window resets:
counting starts again"]
  • In memory: counters live in a ConcurrentHashMap, and restarting the app clears them. That's fine for one server; several servers would need a shared store such as Redis.
  • Behind a proxy: the client IP is request.getRemoteAddr(). Behind a load balancer that would be the proxy's IP, so set server.forward-headers-strategy when you deploy.

CORS

Browsers block a web page on one origin from calling an API on another unless the API allows it. We allow http://localhost:5173 (Vite) and http://localhost:3000 (React/Next), the standard methods, and the Authorization and Content-Type headers. Postman ignores CORS, since it isn't a browser. Your real frontend domain goes on this list at deploy time.

CSRF is off, deliberately

A CSRF attack tricks a browser into sending a request with credentials it attaches automatically, meaning cookies. Our credential is an Authorization header that the frontend sets itself, and a malicious site can't make the browser add it. So CSRF protection isn't needed. If login ever moves to cookies, it must come back on. The comment in SecurityConfig says exactly this.

11Database and Flyway

Two tables, owned by versioned SQL migrations.

Schema created by V1. The two tables aren't linked yet; orders will link them later.

erDiagram
  USERS {
    bigint id PK "identity"
    varchar full_name
    varchar email UK "uk_users_email"
    varchar password_hash "BCrypt"
    varchar role "ADMIN or CUSTOMER"
    boolean enabled
    timestamptz created_at
  }
  PRODUCTS {
    bigint id PK "identity"
    varchar name
    varchar description "max 2000"
    numeric price "12,2"
    varchar category "7 values"
    int stock_quantity
    boolean active "soft delete"
    timestamptz created_at
    timestamptz updated_at
  }

How Flyway works here

  1. At startup, Flyway looks at the flyway_schema_history table to see which migrations have run.
  2. It runs any new V<n>__*.sql files in order and records each one.
  3. Then Hibernate starts with ddl-auto: validate. It checks that the tables match the Java entities and refuses to start if they don't, but never changes them itself.
Changing the schema later

Never edit V1 after it has run anywhere. Add V2__add_orders.sql (and so on) instead. Adding a new Category or Role value also needs a migration, because those columns have CHECK constraints that list the allowed values.

Why not ddl-auto: update? It can add columns but can't rename them, can't move data, and keeps no history. On a real database with customer data, that eventually breaks something.

How we know the tests actually test something

  • Red first: every regression test was written before its fix and seen to fail with the real bug's error.
  • Mutation checks: to test the tests, I broke the code on purpose: removed @PreAuthorize, disabled the rate limiter, renamed a column in V1. Each time the tests failed (expected 403 but was 201, expected 429 but was 200, missing column [stock_quantity]), and then I restored the code.
  • Live checks: each fix was also exercised against the running app and real Postgres, including 20 truly concurrent registrations and a token forged with the old public secret, which was rejected.

16What comes next

Deliberately left out of Phase 1.

  • Refresh tokens and logout: designed together with the frontend, because cookie vs. browser storage changes the CSRF picture.
  • Orders and cart: new tables via V2__…sql, linking users to products (soft delete already keeps those links valid).
  • Deploy settings: the real frontend origin in CORS, server.forward-headers-strategy behind a proxy, and a shared rate-limit store if you run more than one instance.
